Safe Retries: What If the Server Already Did It?

How idempotency keys help APIs handle timeouts, double taps, and page reloads

Written by Harsha Raj Kumar

A post has 1,000 likes. I double-tap to like it, but the number stays the same. I try again. This time it jumps to 1,002.

I only meant to like the post once. The first request may have worked even though the app never showed me the result. The same problem is more serious at checkout. I click Pay, the page times out, and I try again. If the first payment went through, that retry could charge me twice.

You’ve probably seen this warning at checkout: “Please don’t refresh this page while your payment is being processed.” I used to wonder what refreshing could change. If the payment is already in progress, reloading can leave the browser unsure which attempt to resume. That’s the case I want the API to handle safely.

The question I wanted to understand was simple. How can I retry an operation when I don’t know whether it already happened?

A timeout leaves the outcome unknown

A request can time out because it never reached the server, because it’s still running, or because the server finished and the response never came back. All three can look the same on the screen.

Client                              Server
  | ─── POST /payments ───────────────► |
  |                                    | Payment succeeds
  |       Response never arrives       |
  | ─── Retry POST /payments ─────────► |
  |                                    | Retry or new payment?

The second request might have the same amount and recipient. Someone could also intentionally send two $50 payments to the same person. The server needs a way to distinguish two attempts at one payment from two separate payments.

What idempotency means here

In mathematics, an operation is idempotent if applying it again has the same effect as applying it once. abs(-5) gives 5, and applying abs to 5 still gives 5.

For the likes example, compare incrementing a counter with setting my like on the post to true. Repeat the increment and the count goes up again. Repeat the second operation and I still have one like. I’d model the like as a relationship between a user and a post, with a unique constraint on that pair. If I maintain a counter, I’d increment it only when a new like is inserted.

HTTP uses the same idea for the intended effect of methods like PUT and DELETE. A repeated DELETE can return 404 after an initial success while leaving the resource in the same state. A POST /payments needs an explicit retry contract. HTTP semantics, RFC 9110

Give each payment attempt a key

Before sending the payment request, the client generates and saves an idempotency key for that attempt. It sends the key with the request and reuses it if it retries the same operation.

POST /payments HTTP/1.1
Host: api.example.com
Idempotency-Key: 9b1deb4d-3b7d-4bad-9bdd-2b0d7b3dcb6d
Content-Type: application/json

{"checkout_id":"checkout_42","amount":5000,"currency":"usd"}

The client sends the operation and key together. The server checks the key while handling that request.

  • New key. Atomically claim it and start processing. Two requests can reach different server instances at the same time.
  • Same key, still processing. Follow the API’s documented behavior. It might return an in-progress response or let the caller check the operation’s status.
  • Same key, completed. Return the recorded outcome or a reference to the existing payment.
  • Same key, different payment details. Reject the request. Changing the amount from $50 to $500 should never silently reuse the result of the $50 payment.

I’d scope the lookup to the authenticated account and operation and record the fields that define the payment so the server can recognize a changed request. Stripe’s idempotency documentation

Stripe’s engineering write-up walks through the same problem from the API designer’s side, including a request that succeeds but loses its response. Designing robust and predictable APIs with idempotency

What if the page reloads or I open another tab?

I initially thought of this as a session problem. If the browser refreshes after a timeout and generates a fresh key, the server can treat the retry as a new payment. Telling the user to stay on the same page would make the design depend on that page surviving the failure.

I’d tie the key to the checkout attempt. If the app can recover that attempt after a reload, it can recover the same key. A user can make two intentional purchases in one browser session, and one payment attempt can span a reconnect or a new tab.

Pay for checkout_42           → key A
Timeout, reload, retry        → key A
Resume attempt in another tab → key A
Start a separate purchase     → key B

If two tabs independently create different keys for the same checkout, deduplication by key sees two requests. If the business rule is one successful payment per checkout, I’d enforce that on the server too. The key identifies retries of an attempt. The checkout rule protects the business outcome even when the client mishandles its keys.

The crash window a Redis lock can’t close on its own

1. Claim the idempotency key in Redis.
2. Commit the business operation.
3. Save the result under that key.
4. Return the response.

Stop the server after step 2. The change has committed, but Redis still says the request is in progress. If the lock expires and a retry takes over, the new worker could perform the operation again. The lock handled concurrent requests while it was held. Recovering the committed outcome requires a durable record.

If the change lives entirely in one database, I’d commit the change and its completed idempotency record in the same transaction. A retry can then distinguish a transaction that rolled back from one that committed before the response was lost.

For an external payment, I’d persist the attempt before calling the provider, reuse a stable provider idempotency key on retries, and reconcile uncertain outcomes against the provider before attempting a new charge. I’d document how long the API remembers keys. A delayed retry can outlive that window, which makes the durable checkout or payment record important. Stripe’s key retention and retry behavior

What I’d test

I’d let the operation succeed, drop the response, reload the client, and retry. Then I’d check that there’s still only one business effect. I’d also send two copies concurrently, reuse the key with a changed amount, and crash the worker after the provider succeeds but before the application records the result. In that last case, I’d verify that recovery finds the original payment. A 200 OK on the retry tells me very little unless I also check how many payments happened.

My takeaway

I started out thinking a retry should stay in the same session. What I’d preserve now is the same intent, even if the page or connection changes. The client needs to remember which operation it was trying to complete. The server needs to recognize that operation and recover its outcome across failures.

If the operation succeeds and the process dies before telling anyone, what will the next request find?
