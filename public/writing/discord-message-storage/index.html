Why Discord Coalesced Reads Before Moving to ScyllaDB

What happens if I reload after sending a message and join a read that started before my write?

Written by Harsha Raj Kumar

A big Discord server sends an @everyone announcement. Thousands of people open the channel. Many are asking for the same message, and without something to combine those requests, the database has to answer them separately.

I expected Discord’s story to be mainly about Cassandra’s disk reads and garbage collection. Both showed up in the engineering post. I was more interested in how Discord reduced the work reaching the database, and what sharing a read might mean for someone who just sent a message. Discord Engineering’s original write-up

What my first model missed about hot partitions

Discord moved from MongoDB to Cassandra in its earlier messaging architecture. Its Cassandra message cluster grew from 12 nodes in 2017 to 177 by early 2022. Messages were partitioned by (channel_id, bucket), where a bucket was a fixed time window. Within a partition, the Snowflake message ID provided a sortable key. I first imagined splitting a channel after a fixed number of messages. A time window gives the application a predictable way to locate a partition, though a busy channel can still produce a large bucket.

Partition size and partition heat are two different problems. Even a small current bucket can be hot when everyone wants its latest messages. Adding nodes can spread different partitions across the cluster. Reads for one partition still land on the replicas holding it. Those replicas also serve other partitions, so one channel can slow down unrelated queries. Discord’s schema and Cassandra bottlenecks

Why the same read became expensive under load

Write: mutation → commit log and memtable → eventual SSTable flush
Read:  lookup   → memtable and relevant SSTables → reconcile results

On the write path, Cassandra records the mutation in a commit log and updates a memtable. Reads may have to look in memory and across several SSTables on disk. When compaction falls behind, more files may need to be considered. Compaction itself also consumes resources that foreground queries need.

Discord described taking nodes out of rotation to let them compact, then bringing them back to catch up through hinted handoff. JVM pauses added another source of tail latency. My initial storage-engine explanation covered individual read cost. It missed how more concurrent requests could amplify that cost on the same replica nodes. Discord’s account of compaction and JVM pauses

How the slowdown spread

With three replicas and quorum reads, the coordinator needs two responses. A single slow replica needn’t hold up every read if the other two answer quickly. Trouble spreads when enough replicas are busy for a read to wait, and when those same machines serve unrelated partitions. More outstanding work builds up while the slow requests are still running. Compaction then has to compete with that foreground work, even though falling behind on compaction can make later reads more expensive. This feedback loop explains why a hot channel could become an on-call problem for much more than that channel.

Why consistent hashing mattered for coalescing

Discord introduced a Rust data service between its API and database. The first request for a row starts a database query. While it’s in flight, other callers asking for the same row can subscribe to the result.

Same channel → same data-service instance
                           │
             Same row, overlapping reads
                           │
                  One database query
                           │
                  Result to all callers

There’s a reason to route by channel ID first. If identical reads land on separate service instances, each instance can start its own query. Consistent hashing makes it more likely that requests for the same row meet in one place. The channel is the routing key. The particular row being fetched is what makes two requests eligible to share a query. Reads for different rows still require work.

That’s the difference I noticed compared with Snowflake IDs. Any healthy Snowflake worker with a distinct identity can issue the next ID. Here, there’s a reason to give requests affinity to an instance: overlapping callers can share work. Discord reported that hot partitions still occurred after adding this layer, though less frequently. Discord’s Rust data service and routing design

What coalescing leaves exposed

Imagine a burst of 1,000 reads. If they all ask for the same row while one query is in flight on the same instance, they can share it. If they ask for 1,000 different rows, they can still create 1,000 queries against the same hot partition. Routing by channel can also concentrate work on one service instance. If I were evaluating this design, I’d measure coalescing hit rate, distinct reads in flight per channel, and p99 at both the service and the database. Those measurements would tell me whether I also need a concurrency limit for distinct reads.

The question I wish Discord had answered

How did Discord ensure read-after-write consistency through the data service? If my send succeeds and I reload immediately, what ensures the reload includes my message?

The post says Discord used quorum reads and writes. With three replicas and a quorum of two, a successful write’s acknowledgment set and a subsequent read’s response set must intersect if they use the same replica set. For a completed write followed by a fresh read of the same data, that overlap gives the database a replica that received the write. The blog doesn’t spell out how the application handles a reload that joins an earlier query. Discord’s discussion of quorum · Cassandra’s read-repair documentation

Here’s the race I’d test. Assume the requested page should include the new message and that both reads are eligible to share work.

t1  Reader A starts fetching the page.
t2  The database read observes the page before the new message.
t3  The new message is written and acknowledged.
t4  Reader B reloads and joins A’s still-pending read.
t5  Both readers receive the earlier result.

This is a hypothetical timeline. Discord didn’t give enough implementation detail to tell whether it can occur there. The important bit is that B arrived after the write, while the database read it joined observed data before the write. The fact that the query is still in flight tells me very little about the freshness of its result.

If I were building this, I’d first turn the timeline into a test with a controlled pause between the database response and its delivery to subscribers. If the product requires an immediate reload to see the acknowledged write, one option is to bypass reads that began before that acknowledgment on the writer’s next request. I would have liked to see how Discord handled that boundary for sends and edits.

What ScyllaDB changed

Coalescing reduced duplicate work. Discord still needed to improve how the storage tier handled the requests that reached it. Discord cited ScyllaDB’s shard-per-core design, faster repairs, and avoiding the JVM garbage collection issues it had seen. Reverse scans were initially a blocker. Discord needed efficient scans opposite the table’s normal order, and the ScyllaDB team improved that path before the move. Discord’s database evaluation

Shard-per-core changes how work is isolated within a database node. Time buckets still decide which data belongs together, and channel-based routing still decides where requests can share work. Even after changing engines, a high-volume channel can make one partition hot. I’d evaluate the new engine with the actual access patterns, including scans in both directions and foreground reads while compaction is running.

Why the migration stalled at the end

The constraint was to copy trillions of messages while keeping the service online. Discord began dual-writing new data to Cassandra and ScyllaDB. Its initial plan would have routed newer messages to ScyllaDB after a cutoff and migrated older history behind it. That would make reads depend on a time boundary during the transition. The shorter copy estimate made a single cutover practical instead.

The storage setup changed too. Discord used local SSDs for speed and mirrored them to persistent disks with RAID. That matters when interpreting the before-and-after latency numbers, since the database runtime, disk setup, and traffic reaching storage all changed. Discord’s migration plan and storage setup

The initial Spark migration estimate was three months. Discord extended its Rust database library to read token ranges, save progress locally in SQLite, and stream records into ScyllaDB. The new estimate was nine days, and Discord reported a peak of up to 3.2 million messages per second.

At 99.9999% completion, the remaining Cassandra reads timed out on ranges full of tombstones, which are markers for deleted data. Compacting the affected range let the migration finish. Discord sampled reads against both databases and compared results before switching primary traffic in May 2022. I liked this detail because it shows how the source data can bottleneck even a much faster copy pipeline. I’d watch timeouts and progress by token range as well as overall throughput. A nearly complete backfill can still be waiting on its most expensive ranges. Sampled comparisons help detect mismatches before cutover, while edits and deletes during dual writes are cases I’d want to exercise explicitly. Discord’s migration account

What Discord measured afterward

Discord reported going from 177 Cassandra nodes averaging 4 TB of disk each to 72 ScyllaDB nodes with 9 TB each. It also reported less operational firefighting after cutover. Historical-message read p99 went from 40–125 ms to about 15 ms, and insert p99 went from 5–70 ms to about 5 ms. Discord also showed traffic during the 2022 World Cup final as a real example of bursty load. That graph tracks message sends, so I’d use it to illustrate the workload and look for separate latency and error metrics to assess how well the system handled it. I’d read these as production observations after the combined changes. The write-up gives no controlled comparison that isolates how much of the improvement came from coalescing, ScyllaDB, or the storage configuration. Discord’s production results

My takeaway

I started with a broad question about why Cassandra was slow. I came away asking where requests concentrate, how many are doing the same work, and which results can safely be shared. Time buckets organize history. Channel-based routing puts related requests together. Coalescing lets matching reads share a query. ScyllaDB changes the cost of the work that remains. The question I’d bring into a design review is whether the read a caller joins is fresh enough for what the caller was promised.
