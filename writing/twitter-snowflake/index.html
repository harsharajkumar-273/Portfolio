Why Twitter Built Snowflake IDs

Written by Harsha Raj Kumar

Imagine two database shards each insert a tweet and assign it ID 42. Both inserts succeed. Now a client asks for tweet 42. Which one does it mean?

This is my take on Twitter’s original Snowflake design. The bit layout left me with a few questions. What happens when the timestamp runs out? Where do the photos and videos go if the ID is only 64 bits? And if one worker gets overloaded, would I use consistent hashing to route requests? Those questions helped me see where the ID generator’s job ends and the rest of the system takes over.

In 2010, Twitter described moving many systems toward Cassandra or horizontally sharded MySQL. It needed compact IDs that workers could generate independently and that would sort roughly by creation time. Twitter’s original announcement

Three fields make the ID

Snowflake fits a timestamp, a worker identity, and a local sequence into a signed 64-bit integer. In the archived implementation, the worker identity is split into a datacenter number and a worker number. The top bit stays clear within the supported timestamp range.

 1 bit     41 bits               5 bits       5 bits    12 bits
[   0   ][ ms since epoch    ][ datacenter ][ worker ][ sequence ]

The timestamp separates different milliseconds. The datacenter and worker fields distinguish generators operating in the same millisecond. The sequence distinguishes requests handled by one generator during that millisecond. The 41-bit timestamp field covers roughly 69.7 years from the chosen epoch. Archived worker code

What if three tweets arrive in one millisecond?

Say both workers are in datacenter 2, and the elapsed time since the epoch is 1000 milliseconds. Worker 7 handles two requests. Worker 8 handles one.

TimestampWorkerSequencePacked ID
1000704194594816
1000714194594817
1000804194598912

Worker 7 changes the sequence for its second request. Worker 8 can use sequence 0 because its worker field is different. You can reproduce the first number with a few shifts and bitwise ORs. The n suffix makes the values JavaScript BigInts so the same calculation also works for IDs beyond the safe integer range of Number.

(1000n << 22n) | (2n << 17n) | (7n << 12n) | 0n
// 4194594816n

The timestamp is the most significant field, so a larger encoded timestamp sorts later. Look at the last two rows, though. If worker 8 handled its request first, its ID still sorts after worker 7’s IDs. Inside the same millisecond, the worker field decides the order. Clock skew can also put IDs from different workers out of creation order.

Can the ID itself be the cursor?

If I want a feed ordered by Snowflake ID, I only need the last ID from the previous page. IDs are unique, so there is no tie to break. A timestamp alone can skip rows when a page ends in the middle of a group with the same created_at.

SELECT * FROM tweets
WHERE id < :last_id
ORDER BY id DESC
LIMIT 20;

This query assumes a feed ordered by ID, which is roughly chronological. PostgreSQL can use a B-tree primary-key index for the range and order. A feed filtered by another field, such as author, may benefit from a composite index that also includes that field. If the cursor crosses a JSON API, I’d send the ID as a string to preserve all its digits in JavaScript clients. PostgreSQL index ordering

Where the workers still need coordination

Twitter described using ZooKeeper to choose worker numbers at startup, with a configuration override. Once the worker’s identity is assigned, it can generate IDs using its clock and local sequence. Two active generators using the same datacenter and worker pair could generate the same ID if their timestamps and sequences line up. Twitter’s startup and ordering design

What happens when the clock misbehaves?

Twelve sequence bits give a worker 4,096 values per millisecond. If those values run out, the archived worker waits for a later millisecond. If the clock reports a time earlier than the last timestamp the worker used, the worker rejects the request. Reusing an earlier timestamp could repeat a sequence value it had already issued. A backward clock correction can make that worker unavailable until its clock catches up. Overflow and rollback handling in the archived worker

What happens after 69 years?

Existing tweets keep their IDs. The limit is on generating new IDs in the same format. The 41-bit field can represent roughly 69.7 years of milliseconds after the chosen epoch. Using the epoch in Twitter’s archived code, the timestamp reaches the sign bit on July 10, 2080 UTC. The archived code shifts the timestamp into place without an explicit rollover check, so this is the limit of the nonnegative ID range. Epoch and field layout in the archived worker

  • Trade worker slots for time. Giving one bit to the timestamp doubles its range to roughly 139 years and cuts the worker identities from 1,024 to 512. This changes how the bits are decoded, so old and new IDs need a way to coexist.
  • Start a new epoch with a distinct version. Resetting the timestamp alone can recreate old IDs. A version field or a separate namespace gives the new IDs a distinct interpretation. With a version bit, the design has to budget that bit and preserve compatibility with existing IDs.
  • Move to a wider ID. UUIDv7 and ULID each use a 48-bit millisecond timestamp in a 128-bit format. That provides a much longer window and means updating storage, indexes, and APIs that currently expect 64-bit IDs. UUIDv7 specification · ULID specification

Would storing the date separately solve it?

My first thought was that if every tweet already has a created_at column, I can still sort by date after changing the ID format. That works for sorting. The part I missed was that two different timestamps can pack into the same integer when the layout changes.

Same epoch, with worker and sequence bits set to zero:

Old layout: (2⁴⁰ milliseconds) << 22 = 2⁶²
New layout: (2⁴¹ milliseconds) << 21 = 2⁶²

Even though those records were created decades apart, they have the same numeric ID. If id is the primary key, a different created_at value won’t let the second row use that key.

My approach would be to give the new IDs a namespace that cannot overlap with the old one. I’d keep created_at for time-based queries. If the numeric order changes across formats and I still want a chronological feed, I’d sort by created_at DESC, id DESC and carry both values in the cursor. The next page can filter with WHERE (created_at, id) < (:last_created_at, :last_id), so tweets with the same timestamp still have a stable order. If a client only has an ID and needs to decode its timestamp, the ID or its namespace also needs to tell the client which format to use.

Where do the text, photos, and videos go?

The ID identifies the tweet. In a typical design, a tweet record stores its text and references to attached media. An object store can hold the photo or video bytes. For example, a record for tweet 142536789012345678 might reference an image stored under the object key media/7f3c.jpg. This is an illustrative schema.

The same 64-bit ID can identify a short text post or a post with a large video. Its size stays fixed. Fetching and serving the content still depends on the database, the media store, and how much data the client requests.

What if one worker gets overloaded?

Suppose worker 7 has used all 4,096 sequence values for the current millisecond. Its next request waits for the clock to advance. Worker 8 has its own sequence and can still issue IDs during that millisecond. If a worker is overloaded for longer, new requests can go to a healthy worker with spare capacity. Round robin is one possible starting point. Routing based on outstanding requests can help when workers handle uneven loads. These are design options for a Snowflake-style service.

Would I use consistent hashing here?

I wouldn’t start with it. If I’m looking up a tweet, I may need to reach the shard that owns it. If I’m creating a tweet and need a fresh ID, any healthy generator with a distinct worker identity can issue one. Sending every request for the same user to one generator would give that user an affinity the ID format doesn’t need, and a busy user could concentrate load on one worker.

Consistent hashing helps when a storage or cache layer needs stable placement as nodes come and go. Snowflake workers each keep their own timestamp and sequence, but a caller can switch workers because the worker identity is encoded in the result. That’s what makes the requests interchangeable from the caller’s point of view.

My takeaway

The useful part of Snowflake is where it puts the coordination. Give each worker a distinct identity up front, then let it allocate IDs using its own clock and counter. That keeps a shared counter out of the request path and lets callers spread load across workers. In exchange, you have to manage worker identities, handle clock rollback, and accept that sorting the IDs gives approximate time order.
