What happens when curl connects to an HTTPS server?

Written by Harsha Raj Kumar

If curl says it connected to port 443, has the server seen your HTTP request yet? The easiest way to see the gap is to watch a single request in verbose mode.

Run one request

curl -v --http1.1 https://example.com/ -o /dev/null

-v shows connection details. --http1.1 gives us a repeatable example over TCP, and -o /dev/null keeps the response body out of the terminal. The excerpts below come from one run. Your resolved addresses and TLS details may differ.

1. Resolve the name and connect

* Host example.com:443 was resolved.
*   Trying [2606:4700:10::6814:179a]:443...
* Connected to example.com (2606:4700:10::6814:179a) port 443

The name resolved to several addresses, and this run connected over IPv6. The Connected line tells us the TCP connection opened. To see the actual SYN, SYN-ACK, and ACK packets, you’d use a packet capture. TCP gives the application a reliable, ordered stream of bytes. TCP specification

2. Negotiate TLS

* ALPN: curl offers http/1.1
* (304) (OUT), TLS handshake, Client hello (1):
* (304) (IN), TLS handshake, Server hello (2):
* ALPN: server accepted http/1.1
* SSL certificate verify ok.

The trace reported TLS 1.3. During the handshake, the client and server establish encryption keys. Curl checks that the server certificate is trusted and valid for example.com. ALPN is how they agree to speak HTTP/1.1 over this connection. At this point, we still haven’t reached the GET.

3. Send the request and read the response

> GET / HTTP/1.1
> Host: example.com
< HTTP/1.1 200 OK

> marks what curl sent and < marks what it received. Curl displays those lines in readable form because it sits at the client endpoint. On the wire, TLS encrypts the HTTP message.

The seven OSI layers, from the request to the wire

The OSI model describes networking as seven layers. Each layer answers a different question, from what the message means to how a signal moves across a link. The curl trace gives us clues about several of those layers. For the rest, we can follow what happens to the bytes after curl hands them to the operating system. OSI Basic Reference Model

7. Application — What does the message mean?

HTTP defines what GET / asks for and what 200 OK means. Curl is the program using the protocol. Name resolution happens earlier in the example. DNS is also an application-layer protocol when a DNS lookup is needed, although this trace doesn’t show whether the resolver sent a query or used a cached answer.

6. Presentation — How is the data represented?

The receiver needs to know how to interpret the bytes. An HTTP response might declare Content-Type: text/html; charset=utf-8, which tells the client the document format and character encoding. Compression is another example of a transformation that endpoints need to agree on. The OSI model gives data representation its own layer. In Internet software, HTTP metadata and application libraries often handle that work directly.

5. Session — How is an ongoing exchange coordinated?

The OSI session layer describes managing a dialogue between endpoints, including whose turn it is to send and where an interrupted exchange can resume if the protocol supports checkpoints. A web application may instead maintain continuity across many HTTP requests with a session cookie. That is a familiar example of session state, implemented at the application level. This curl request has no separate OSI session protocol to point to.

4. Transport — Which connection gets these bytes?

TCP connects a local port to port 443 at the remote address. It numbers bytes so the receiver can put them in order and uses acknowledgments and retransmissions to recover from loss. Flow control keeps the sender from overrunning the receiver. The Connected line marks the point where curl has a transport connection it can use for TLS.

3. Network — Where is the destination?

IP supplies source and destination addresses. The operating system uses its routing table to select an outgoing interface and next hop. Routers then forward the packet toward its destination. The IPv6 address in curl’s Trying line is the remote destination for this connection.

2. Data Link — How does the packet reach the next hop?

On Ethernet, the IP packet rides inside a frame addressed to a device on the local link. For a remote server, that local destination is usually the default gateway. A router removes the incoming link-layer frame and sends the forwarded IP packet in a new frame on the outgoing link. So the first Ethernet frame can be addressed to the gateway’s MAC while the IP packet inside is addressed to the remote server.

1. Physical — How do the bits travel?

The hardware sends bits as signals suited to the medium, such as electrical signals on copper, pulses of light in fiber, or radio waves over Wi-Fi. Curl can report that the connection worked. To check a physical link, start with the interface’s link status or radio signal, since curl cannot tell you which medium carried each hop.

Encapsulation — What gets wrapped around what?

For an Ethernet hop in this example, the HTTP message is encrypted into TLS records. TCP carries those bytes in segments, IP carries the segments in packets, and Ethernet carries the packets in frames with a header and an error-detection trailer. The physical link transmits the frame as signals. At the receiving endpoint, those steps are reversed so the HTTP server can read the request. One HTTP message can span multiple segments and frames.

The mapping is approximate. For this request, HTTP runs over TLS, TLS uses TCP, and TCP travels over IP. The link layer carries traffic on each local hop. On an Ethernet network, a request to a remote server can have the router’s MAC address as its first-hop destination while the IP packet is still addressed to the remote server. The curl trace shows the IP address. A packet capture can show the local frame. Internet host communication layers

For debugging, look for the last line that succeeded. Connected gets you through TCP. SSL certificate verify ok. gets you past certificate verification. An HTTP status means you received an HTTP response. If you try HTTP/3, the transport looks different because HTTP/3 uses QUIC over UDP. HTTP/3 specification
